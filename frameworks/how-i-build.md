# How I Build

Not a methodology. A short list of behaviors that keep showing up the same way whether the work is an enterprise workflow, a personal tool, or a portfolio piece. Naming it once so I stop reinventing it per project.

1. **Start with the problem, not the artifact.** Most requests arrive already wearing a proposed solution. Instead of building the dashboard/app/agent as asked, I go find the workflow and failure mode underneath the ask first.
2. **Get to evidence fast.** Talking about an idea has a short half-life before it stops teaching me anything new. Instead of another round of discussion, I'd rather run the smallest thing that produces a real answer.
3. **Build enough to test the thinking, not to plan it away.** Analysis that never becomes something usable doesn't hold my interest. Instead of a spec that tries to resolve every unknown up front, I build the sliver that tells me if the idea holds up.
4. **Use AI to collapse handoffs, not just speed up old steps.** The interesting move isn't typing faster. It's removing a whole handoff that used to require a person. Instead of automating the old process, I look for where the process itself was only there because a handoff used to be necessary.
5. **Keep judgment with the human.** AI moves faster than judgment can verify, so the verification has to stay mine. Instead of trusting output because it's fluent, I check it against evidence before it becomes a decision.
6. **Make assumptions, confidence, and gaps explicit.** Silent assumptions are where projects quietly go wrong. Instead of letting an unstated guess ride along, I write down what I'm assuming, how sure I am, and what's still unknown.
7. **Prefer small working loops over ceremony.** A narrow thing that's actually running beats a broad thing that's still hypothetical. Instead of a process built to look thorough, I want the shortest loop that produces a real, checkable result.
8. **Codify what repeats, retire what doesn't.** If the same shape of problem shows up twice, it's worth naming; if it doesn't, it's not worth a framework. Instead of building reusable systems speculatively, I wait for the second occurrence before I generalize.

If someone asks what AI-native product work looks like in practice, this is closer to the real answer than any tool list: same judgment, applied through a faster, more collapsible process, with the human still doing the checking.
